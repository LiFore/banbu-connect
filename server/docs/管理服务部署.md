# Banbu Connect 管理服务部署

管理服务（`boxctl server`）部署在公网服务器上：在网页上维护订阅、节点、代理组、线路和规则，发布给绑定的 Banbu Connect 客户端，并托管客户端更新包。它是一个 Go 二进制，前端已内嵌，数据在 SQLite（`/var/lib/banbu-connect`）。

## 1. 准备

| 项 | 要求 |
|---|---|
| 服务器 | Linux x86_64 或 arm64，带 systemd |
| 端口 | 自签名证书默认 `8443`；有域名证书用 `443`；放在反向代理后面只需代理的 `443` |
| 域名 | 可选。没有域名就用自签名证书，客户端绑定时要填证书指纹 |
| 构建机 | Go、Node.js、bash（Windows 用 Git Bash） |

## 2. 构建

在本仓库根目录：

```bash
./scripts/build-server.sh amd64    # arm64 服务器用 arm64
```

产物：`dist/boxctl-linux-amd64`。

## 3. 准备初始配置（可选）

新服务第一次启动时，如果数据目录的 `seed/` 下有文件，并且还没有任何节点和代理组，就导入一次作为初始配置；之后不再导入。

- `*.yaml`：Mihomo 配置，导入其中的 `proxies`（含 `dialer-proxy`）、`proxy-groups`，以及 boxctl 的扩展字段 `x-strict`（严格组）、`x-selections`（线路）。
- `*.txt`：每行一条规则，作为下发规则。
- `Claude`、`ChatGPT` 组总是严格组：成员里能走到 DIRECT 的组（如「代理模式」）会换成它除 DIRECT 以外的成员，否则客户端的 Kill Switch 无法生成配置。
- 导入失败时清空已导入的内容，下次启动重试，原因见日志。

把一台已配置好的管理服务导出成初始配置：

```bash
boxctl server export-seed -data-dir /var/lib/banbu-connect -out ./seed
# 本地开发环境：cd boxctl && go run ./cmd/boxctl server export-seed -data-dir ../.dev/server -out ../dist/seed
```

生成 `config.yaml` 和 `rules.txt`。代理组的动态成员按导出时的结果写成固定成员；停用的节点不导出。

> **这些文件含节点密码和代理账号，不要放进仓库。** 本仓库的 `dist/` 已被 `.gitignore` 忽略；当前的初始配置在 `dist/seed/`。导入成功后可以从服务器上删掉 `seed/`。

## 4. 安装

```bash
# 上传（在构建机上）
scp dist/boxctl-linux-amd64 deploy/banbu-connect.service root@<服务器>:/tmp/
scp -r dist/seed root@<服务器>:/tmp/seed        # 没有初始配置就跳过

# 在服务器上
install -m 0755 /tmp/boxctl-linux-amd64 /usr/local/bin/boxctl
cp /tmp/banbu-connect.service /etc/systemd/system/
```

按证书方式改 `/etc/systemd/system/banbu-connect.service` 的 `ExecStart`：

| 方式 | ExecStart 参数 | 客户端绑定 |
|---|---|---|
| 自签名证书（默认） | `-listen 0.0.0.0:8443` | 地址 `https://<IP或域名>:8443`，要填证书指纹 |
| 已有证书 | `-listen 0.0.0.0:443 -tls-cert /etc/banbu-connect/fullchain.pem -tls-key /etc/banbu-connect/privkey.pem` | 地址 `https://<域名>`，不填指纹 |
| 反向代理后面 | `-listen 127.0.0.1:8080 -plain-http` | 地址 `https://<域名>`，不填指纹，见第 6 节 |

服务以 systemd 的临时用户运行（`DynamicUser=yes`），只能写自己的数据目录。用已有证书时，证书文件要让所有用户可读，或改用反向代理。

启动，并放入初始配置：

```bash
systemctl daemon-reload
systemctl enable --now banbu-connect          # 第一次启动，创建数据目录
systemctl stop banbu-connect

# 放入初始配置，属主改成服务的用户（与数据目录相同）
cp -r /tmp/seed /var/lib/banbu-connect/seed
chown -R --reference=/var/lib/banbu-connect /var/lib/banbu-connect/seed
chmod 0700 /var/lib/banbu-connect/seed && chmod 0600 /var/lib/banbu-connect/seed/*

systemctl start banbu-connect
journalctl -u banbu-connect -n 20 --no-pager  # 看到 "imported seed config ... nodes=… groups=… rules=…" 即导入成功
rm -rf /tmp/seed /tmp/boxctl-linux-amd64
```

开放端口（以 ufw 为例）：`ufw allow 8443/tcp`。云服务器还要在安全组里放行。

## 5. 首次登录

- 打开 `https://<服务器>:8443`。自签名证书时浏览器会提示不安全，确认后继续。
- 初始密码：`cat /var/lib/banbu-connect/initial-password`。首次登录要修改，修改后这个文件自动删除。
- 忘记密码：`boxctl reset-password -data-dir /var/lib/banbu-connect`，然后执行下面的属主修正。

> 用 root 对数据目录运行 `reset-password`、`export-seed` 后，数据库文件可能变成 root 所有，服务就写不了。之后执行一次：
> `chown -R --reference=/var/lib/banbu-connect /var/lib/banbu-connect && systemctl restart banbu-connect`

## 6. 反向代理（可选）

由代理负责 HTTPS 和证书续期，管理服务只监听回环地址。代理必须设置 `X-Real-IP`，「客户端」页面才能显示客户端的真实 IP。

Caddy：

```
connect.example.com {
	reverse_proxy 127.0.0.1:8080 {
		header_up X-Real-IP {remote_host}
	}
}
```

Nginx：

```nginx
server {
    listen 443 ssl http2;
    server_name connect.example.com;
    ssl_certificate     /etc/letsencrypt/live/connect.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/connect.example.com/privkey.pem;
    client_max_body_size 512m;   # 上传客户端更新包

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

## 7. 日常使用

1. **订阅 / 节点 / 代理组**：维护节点和代理组。
2. **线路与规则**：设置每个手动选择组的默认成员，以及放在客户端自定义规则之前的规则。
3. **发布**：把当前配置发布成新版本。不发布时客户端收不到任何修改。
4. **客户端**：新建客户端令牌（只显示一次），把「服务端地址、令牌、证书指纹」发给用户。用户在 Banbu Connect 的「高级 → 管理服务」里填写并绑定，之后每 5 分钟同步一次。不再使用的令牌在这里吊销。
5. **客户端更新**：上传安装包和 `.sig` 签名，填版本号和平台，打开「发布」后客户端才会收到。安装包由 `scripts/build-app.sh` 生成，构建机上要有签名私钥 `~/.tauri/banbu-connect.key`，见 `client/README.md`「应用更新（OTA）」。
6. **Claude 账号**：读取登录邮件用 Gmail API，第一次使用前：
   1. 在 Google Cloud 控制台新建项目，启用 Gmail API。
   2. 「OAuth 同意屏幕」选「外部」，添加范围 `gmail.readonly`，**发布为正式版**（停在「测试」状态时，授权 7 天后失效；未经验证会显示警告页，自用可以继续）。
   3. 「凭据 → 创建 OAuth 客户端 ID」，类型选「桌面应用」，把客户端 ID 和密钥填到「Claude 账号 → Google OAuth 客户端」。

   然后登记每个 Claude 账号的邮箱（它自己的 Gmail），点「授权 Gmail」：用这个 Gmail 登录并允许只读访问，浏览器会停在打不开的 `http://127.0.0.1:53682/…`，把地址栏的完整地址粘贴回来。指定哪些客户端可以用，点「测试 Gmail 授权」确认。客户端概览上点「登录」即可在本机发起 Claude Code 登录，流程见 `client/README.md`「Claude 账号登录」。服务器要能访问 `oauth2.googleapis.com` 和 `gmail.googleapis.com`。

## 8. 文件存储：阿里云 OSS（可选）

客户端更新包和「文件」页上传的文件默认存在数据目录（`releases/`、`files/`），客户端经管理服务下载。配置阿里云 OSS 后，新文件存到 OSS，客户端用 15 分钟有效的签名地址直接从 OSS 下载，不占服务器带宽。

1. 在 OSS 控制台建一个 **私有** Bucket（读写权限选「私有」）。
2. 建 RAM 子账号，只授权这个 Bucket：`oss:PutObject`、`oss:GetObject`、`oss:DeleteObject`、`oss:InitiateMultipartUpload`、`oss:UploadPart`、`oss:CompleteMultipartUpload`、`oss:AbortMultipartUpload`，以及 `oss:GetBucketCors`、`oss:PutBucketCors`（用于自动配置跨域）。
3. 管理服务「文件」页 → 存储设置：填写地域（如 `cn-hangzhou`）、Bucket、AccessKey，点「测试连接」。
4. 测试结果提示跨域规则不允许时，先保存，再点「自动配置跨域」：给 Bucket 加一条允许管理页面地址 PUT、暴露 `ETag` 的 CORS 规则。浏览器分片直传云盘文件需要它；更新包由管理服务上传，不需要。
5. 打开「使用 OSS 存储新文件」并保存（保存前会再测一次读写）。已有文件可以点「迁移到 OSS」，迁移后删除本机副本。

注意：

- AccessKey Secret 加密保存在数据库里，页面上不回显。
- 未完成的分片上传 24 小时后放弃；建议在 Bucket 的生命周期规则里加「碎片过期删除」（如 2 天）。
- 0.2.10 及以前的客户端不认下载跳转，下载更新包时管理服务会从 OSS 读出来转发，仍然可以更新。

## 9. 通知与用量提醒

「通知」页配置推送渠道和提醒规则，管理服务每 5 分钟检查一次：

- **推送渠道**：Bark（iOS，粘贴 Bark 应用里的推送地址或 key，可填多个设备；自建服务器时改服务器地址）；飞书群自定义机器人（Webhook 地址，开启签名校验时填密钥）。点「发送测试」确认能收到。
- **节点流量**：选节点或代理组，按每天或每月设上限（GB）。数据来自客户端上报的代理连接统计，链式代理的每一跳都算；没开连接上报的客户端不计入。
- **订阅**：已用流量比例、剩余流量、离到期天数，数据来自机场返回的 subscription-userinfo。
- **AI 账号**：客户端上报的额度，超过已用比例时提醒；每个额度窗口只提醒一次，重置后重新计算。
- **订阅自动更新**：管理服务按每个订阅的「自动更新（小时）」定时拉取。节点有变化且影响下发内容时自动发布新版本并推送摘要；失败或需要手动确认（会删除仍被代理组使用的节点）时推送原因。注意：自动发布会把当时的草稿一起发布出去。

同一件事只提醒一次，条件恢复后或进入新的统计周期才会再次提醒。最近的通知（含推送失败原因）在页面底部。

## 10. 升级、备份与排错

- **升级**：重新构建，替换 `/usr/local/bin/boxctl`，`systemctl restart banbu-connect`。数据库迁移在启动时自动执行。
- **备份**：整个 `/var/lib/banbu-connect`。其中 `device.key` 是节点凭据和已发布配置的加密密钥，丢了就无法解密，必须和数据库一起备份。
- **迁移到新服务器**：复制整个数据目录（含 `device.key`）。只想要配置、不要发布历史和客户端令牌时，用 `export-seed` 导出初始配置，在新服务器上按第 3、4 节导入。已绑定的客户端要用新令牌重新绑定。
- **日志**：`journalctl -u banbu-connect -f`。
- **导入没有生效**：初始配置只在还没有任何节点和代理组、并且以前没导入过时才导入。日志里有 `import seed config failed` 时按原因修正文件，再重启服务。
