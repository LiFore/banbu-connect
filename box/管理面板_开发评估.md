# 端侧管理面板（含 proxy-guard）开发评估

版本：0.1 | 日期：2026-10-28 | 输入：《端侧软路由盒子_技术方案与实施路线 v1.0》、`E:\SystemProject\sub-store\{script.js, operate.js, demo.js, test.yaml}`

## 0. 已锁定的前提

| 项 | 结论 |
|---|---|
| 使用范围 | 企业内部自用，主路由部署，小范围试点（首版不做 OTA 和集中运维） |
| 底座 | ImmortalWrt（锁定版本）+ Nikki + Mihomo |
| DNS / Kill Switch | redir-host；proxy-guard 与健康状态联动；DIRECT 规则目标自动同步进直连白名单；首版关闭 IPv6 转发 |
| 进程架构 | 同一个 Go 代码库，编译成单个二进制，以两个进程运行：`boxctl panel` 和 `boxctl guard`，分别是两个 procd 服务，通过 unix socket 通信 |
| 技术栈 | 后端 Go + SQLite；前端 React + Ant Design，构建后通过 `embed` 打进二进制 |
| 范围 | 面板不接管 WAN/LAN/DHCP，这部分继续用 LuCI；现有脚本的分组和规则结构做成出厂默认模板，不做通用导入器 |
| 订阅处理 | Sub-Store 的能力内化到 Go 后端，盒子上不再运行 Node.js |

## 1. 进程与职责划分

```
┌──────────── boxctl panel（非关键路径，可随时重启） ───────────┐
│ React UI ── REST/WS ── 数据模型(SQLite) ── 订阅引擎 ── 配置生成器 │
│                                   │                 │          │
│                         Mihomo API(127.0.0.1)   产物：           │
│                                                 ① mihomo.yaml   │
│                                                 ② guard-policy.json│
│                                                 ③ dnsmasq nftset 片段│
└──────────────────────────────┬──────────────────────────────────┘
                     unix socket：提交策略 / 查询状态
┌──────────── boxctl guard（关键路径，最小依赖） ───────────────┐
│ 独立 nft 表 inet proxy_guard ─ 集合维护 ─ 健康状态机 ─ conntrack 清理 │
│ 启动早期加载上一份已知可用的策略；panel 不在线时照常工作               │
└──────────────────────────────────────────────────────────────────┘
```

- **guard 只认已校验的策略文件**，不读 SQLite，也不直接解析 Mihomo 配置。panel 生成 `guard-policy.json` 时附带版本号，和 `mihomo.yaml` 属于同一个配置版本，回滚时两者一起回滚。
- **guard 不依赖 panel 存活。** 健康检查（Mihomo API、真实出口探测）由 guard 自己执行，避免 panel 挂掉时状态机跟着失灵。
- **写权限边界。** Nikki 的 mixin 只负责透明代理相关字段：监听端口、tproxy/redir、DNS 监听地址；面板负责 proxies、proxy-groups、rules、rule-providers、dns 策略、sniffer、geox。Nikki 的 LuCI 配置页需要隐藏。

## 2. 现有脚本拆解：要内化的功能

### 2.1 `operate.js`：节点清洗与重命名

| 现有逻辑 | 面板中的对应功能 |
|---|---|
| 73 个地区的旗帜和中英文关键词表，长关键词优先匹配 | 「地区识别」内置字典，可在 UI 中维护；识别结果存成节点的结构化字段 `region` |
| 无法识别地区的节点直接丢弃，这会顺带丢掉「剩余流量 / 套餐到期 / 官网」这类信息节点 | 拆成两步：①按名称规则过滤信息节点；②地区无法识别时可选择丢弃或归入「其他」 |
| 重命名为 `地区 - 序号 - 订阅名` | 显示名模板 `{region} - {seq:02} - {sub}`，**只用于展示**，引用时使用稳定 ID |
| 无 | 解析响应头 `subscription-userinfo`，在订阅卡片上显示已用/总流量和到期日，代替信息节点 |

### 2.2 `script.js`：全局覆写

| 现有逻辑 | 面板中的对应功能 |
|---|---|
| `customRules`：DOMAIN-SUFFIX / KEYWORD / DST-PORT / AND(...NETWORK,udp) | 规则编辑器，支持逻辑规则；常用服务做成「服务预设」，一个预设包含域名列表、QUIC 阻断和目标组 |
| 17 个 rule-provider（Loyalsoldier、blackmatrix7） | 规则集目录：内置条目、支持自定义 URL、配置下载镜像，记录更新时间和条目数 |
| 规则顺序：自定义 → 广告 → 直连 → GEOIP → 服务 → 代理 → MATCH | 规则按「分段」组织：自定义 / 服务 / 直连 / 代理 / 兜底，段内可拖拽排序 |
| 按地区正则生成 url-test 组和 select 组 | 「动态成员」代理组：成员由过滤条件决定（地区 / 订阅 / 协议 / 标签），不再依赖名称正则 |
| 按订阅名生成自动组，`subNameDisplayMap` 显示名 | 订阅本身带显示名；「按订阅生成自动组」作为模板中的开关 |
| 把 ISP 代理硬编码进 proxies，`dialer-proxy` 指向「链式拨号代理组」 | ISP 代理节点表单 + 前置代理选择器（见 3.3 节） |
| 用名称子串排除 ISP 节点（`proxiesWithoutISP`） | 改用节点类别标签 `kind=isp` 过滤 |
| DNS：default-nameserver、nameserver-policy（订阅节点域名走国内 DNS）、fallback-filter | DNS 页面提供模板；节点域名自动加入 nameserver-policy |
| sniffer、geox-url 加速前缀、unified-delay、tcp-concurrent、store-selected | 「高级参数」页，给出合理默认值 |
| `ping0.cc` 路由到 Claude 组，用来查看出口 IP | 产品化为「出口检测」：选择任意组或节点，显示出口 IP、ASN、地区、IP 类型 |

### 2.3 `demo.js`

这是 Sub-Store 官方的脚本说明模板，没有业务逻辑。对我们有用的信息是 Sub-Store 内部节点结构中的私有字段（`_subName`、`underlying-proxy` 等）。面板的节点结构与 Mihomo 对齐即可，不需要兼容 Sub-Store 的私有字段。

### 2.4 `test.yaml`：样本订阅

共 125 个节点，都来自同一个订阅。协议分布：anytls 98、hysteria2 16、vless+reality 6、trojan 5。前几个节点是信息节点。**订阅解析器的首批必须支持 anytls、hysteria2 和 vless-reality**，这也说明 Mihomo 版本必须锁定在支持 anytls 的版本上。

## 3. 三类应用场景的配置设计

### 3.1 外购的 Clash 订阅

1. 填写 URL，可选：UA、拉取方式（直连 / 经现有代理）、更新周期。
2. 拉取后先预览：识别出的节点数、被过滤的信息节点、地区分布、协议分布、与上次相比的增减。
3. 确认后入库。节点 ID = `hash(协议, server, port, 关键凭据)`。机场改名不影响引用；节点被删除时，提示哪些组和链路受影响。
4. 解析格式：Clash/Mihomo YAML、Base64 编码的 URI 列表、纯 URI 列表。

### 3.2 自建隧道

- **粘贴分享链接**（`vless://`、`hy2://`、`anytls://`、`trojan://`、`ss://`、`tuic://`），也支持粘贴一段 Mihomo YAML 片段。
- **或按协议填表单**。表单由协议 schema 驱动，只展示该协议的必填和常用字段，Reality、传输层等放在折叠区。
- 保存前做一次真实连通性测试：延迟加出口 IP。

### 3.3 ISP 代理（curl 模式）

- 输入框直接接受 curl 写法，例如 `curl -x http://USER:PASS@host:port`、`--proxy socks5h://...`、`-U user:pass`，以及 `host:port:user:pass` 这类常见格式。解析成 http 或 socks5 节点。
- **前置代理**：在下拉框中选择一个节点或代理组，生成 `dialer-proxy`，界面上展示「LAN → 机场节点 → ISP 代理 → 目标」的链路。
- 用户名参数助手（可选）：不少供应商把国家、粘性会话等参数编码在用户名里。可以提供「国家 / session」字段帮助拼接，但不硬编码任何一家供应商的格式。
- 保存后自动做出口检测，确认出口 IP 是 ISP 类型、地区符合预期。

## 4. proxy-guard 在面板中的配置项

| 配置 | 说明 |
|---|---|
| 保护模式 | A 全局故障关闭 / B 国内直连 + 境外故障关闭（默认）/ C 仅严格域名保护 |
| 严格策略组 | 在代理组上勾选「严格」后：①生成器检查从该组出发的所有路径都不包含 DIRECT；②这些组的规则域名会被展开，写入 dnsmasq nftset 生成 `strict_v4`；③自动在这些域名的规则前插入 QUIC 阻断 |
| 直连白名单 | 包含手动条目（带来源标注和到期时间，如境外游戏）和从 DIRECT 规则自动同步的条目（只读展示） |
| 国内 IP 数据源 | 数据源、更新周期、当前版本和条目数 |
| 健康检查 | 检查间隔、失败阈值、恢复阈值、探测目标；切换中默认保持阻断 |
| 状态页 | 当前状态、最近的状态切换记录、各集合的条目数、nft 规则自检结果、一键自检 |

**兜底规则 `MATCH` 的语义需要在界面上说清楚**：在模式 B 下，`MATCH → DIRECT` 只会对国内 IP 和白名单生效，其余境外流量会被 guard 拦截。保存时如果检测到这种组合，要给出提示。

## 5. 现有脚本里的问题（迁移时不要照搬）

| # | 位置 | 问题 | 影响 |
|---|---|---|---|
| 1 | `script.js:206-237` | ISP 代理的用户名和密码**明文硬编码在脚本里** | 凭据泄漏风险。**建议立即在供应商后台轮换这两组凭据**；新面板把凭据加密存储，并在日志和诊断包中脱敏 |
| 2 | `script.js:41-45` | `DOMAIN-KEYWORD,claude,Claude` 排在 `AND,((DOMAIN-KEYWORD,claude),(NETWORK,udp)),REJECT` 之前。规则按第一条命中生效 | **Claude 的 QUIC 阻断实际上从未生效**（anthropic 同理）。生成器应自动把 QUIC 阻断放在对应服务规则前面 |
| 3 | `script.js:248-271、332-362` | 地区正则形如 `/ 香港 | HK|.../`，带有多余空格（疑似被自动排版工具插入），而重命名后的格式是 `香港 - 01 - xxx`，开头没有空格 | 地区组很可能匹配不到节点，退化成「手动选择」；改用结构化的 `region` 字段可以彻底避免这类问题 |
| 4 | `script.js:254` | TW 组的正则包含 `🇨🇳` 和 `Wan` | 中国旗节点和名称含 wan 的节点会被误分进台湾组 |
| 5 | `script.js:130、171` | `telegramcidr` 定义了两次，后一次覆盖前一次 | 前一个定义是死代码，容易造成困惑 |
| 6 | `script.js:375-385、445-457` | 「代理模式」组包含 DIRECT，而 Claude、ChatGPT 组又把「代理模式」列为成员 | 严格目标存在一条可以走到 DIRECT 的路径，与 Kill Switch 的原则冲突。生成器做「严格组」检查时必须能拦住这种情况 |
| 7 | `script.js:447` | ChatGPT 组硬编码了「烟火云CN2自动选择组」 | 订阅改名或删除后，这个引用会悄悄失效 |
| 8 | `script.js:488-493` | 名为 `cnDnsList` 的列表里包含 `tls://8.8.8.8:853`，并被用于 `geosite:cn` 和节点域名的解析 | 国内域名可能拿到非最优的解析结果；在 redir-host 模式下，还会影响 cn 集合的判断 |
| 9 | `script.js:518-526` | 使用的 `fallback` / `fallback-filter` 是旧式写法 | 在 redir-host 加 nameserver-policy 的方案下应该去掉，统一到一套 DNS 策略 |
| 10 | `script.js:545`、多个 rule-provider | 依赖第三方 GitHub 加速域名和 raw.githubusercontent | 存在供应链和可用性风险；改为内部镜像或面板侧缓存，并做哈希校验 |

### 降低成本的关键：直接复用 Mihomo 的 Go 包

后端也是 Go，因此可以直接 import Mihomo 的代码，不用重写 Sub-Store 的解析器：
- `common/convert`：分享链接和 v2rayN 订阅转换成 Clash 代理配置的 map；
- `adapter.ParseProxy`：用与运行时完全相同的逻辑校验每个节点的字段；
- 配置解析：在提交前做和运行时一致的配置校验，作为 `mihomo -t` 之外的第二道检查。

预计能让 M2、M3、M8 节省 **8–12 人日**，而且协议支持天然与锁定的 Mihomo 版本一致。Mihomo 是 GPL-3.0，企业内部自用不涉及分发义务；将来如果对外分发，面板也必须以 GPL 开源。

## 8. 主要风险

| 风险 | 应对 |
|---|---|
| Mihomo 升级导致字段或协议行为变化 | 锁定版本；Go 包和运行时二进制使用同一个 tag；升级前跑黄金文件测试和故障注入 |
| 严格域名展开得不全（CDN、新子域名） | 服务预设由团队维护并定期验证；结合出口检测和连接日志发现漏网的域名 |
| redir-host 下 DNS 集合与 TTL 不同步 | 集合超时时间设为 ≥ TTL 并留余量；严格域名走代理侧 DNS；故障注入测试中加入 TTL 过期的场景 |
| 订阅源或规则源在国内不可达 | 默认经代理拉取；面板侧缓存；内部镜像 |
| 前端工作量被低估（表单和拖拽交互多） | 先做表格加表单，拓扑图放到 P1；协议表单由 schema 驱动，避免逐个手写 |
